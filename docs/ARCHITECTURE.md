# ManicERP architecture

## 1. Context and constraints

ManicERP is a modular monolith for Zimbabwean local authorities. The build
environment inspected for this implementation has PHP 8.4, PostgreSQL 16 without
PostGIS, Node 20, pnpm 10, no Redis and no Flutter SDK. Those facts drive several
reversible decisions recorded at the end of this document.

One backend serves three surfaces:

1. Staff ERP — Inertia/React pages under `/` (staff middleware).
2. Citizen portal — Inertia/React pages under `/portal`.
3. Citizen mobile app — versioned JSON API under `/api/v1`.

## 2. Repository layers

```
backend/
  app/
    Http/Controllers/{Accounting,Admin,Ai,Api,Auth,Customer,Licensing,Revenue}/
    Modules/
      Platform/   Models, Services, Http/Middleware
      Accounting/ Models, Services
      Revenue/    Models, Services, Gateways, Contracts
      Customer/   Models, Services
      Licensing/  Models, Services, Jobs
      Ai/         Models, Services
    Support/      Money, Decimal, TenantModel
  database/migrations/central/   council directory and identity
  database/migrations/tenant/    one copy per council database
  resources/js/                  Inertia pages, layouts, components
  routes/web.php, routes/api.php
  tests/                         PostgreSQL-backed feature and unit tests
mobile/                          Flutter citizen app source
docs/                            this documentation set
```

Module boundaries are directories plus explicit service classes. There are no
cross-module database joins: modules share the same tenant database by design,
but call each other through services and contracts, not by reaching into another
module's tables from controllers.

## 3. Council isolation (the security boundary)

### Two kinds of database

- **Central (`pgsql`)** — `councils`, `council_domains`, `council_modules`,
  `users`, `roles`, `council_memberships`, sessions, cache, jobs, failed jobs,
  personal access tokens, platform audit, AI usage. This is the control plane.
- **Tenant (`tenant`)** — one physical PostgreSQL database per council holding
  operational data: audit, documents, accounting, revenue, billing, cashier,
  bank and citizen-link tables.

`councils.database_name` is generated by `CouncilProvisioner` and never accepted
from a client. `TenantManager` validates the identifier against
`^[a-z][a-z0-9_]{2,62}$` before pointing the `tenant` connection at it.

### Resolution

`ResolveCouncil` middleware resolves the council in this order:

1. **Verified host** — `council_domains.host` (lower-cased). A host match is
   authoritative: if the user is not a member there, access is refused rather
   than silently falling back.
2. **Session selection** — only for a council where the authenticated user has an
   active membership. This supports local development and multi-council staff.
3. **Single active membership** — the only membership becomes the context.
4. **Otherwise** — the user is sent to the council chooser.

For the API, the council comes from a **token ability** (`council:CODE`) and is
re-validated against the user's membership. A request body or query parameter
`council_id` is never read.

A host or session council never overrides a missing membership. Every request
re-checks membership status and `revoked_at`. The tenant connection is
re-established only when the database differs, which is also what lets tests
hold a transaction.

### Queues and scheduled work

Queue/cache/session storage is central (`database` drivers). A queued job must
carry a validated council identifier in its constructor and run its work inside
`TenantManager::runFor($council, ...)`, which restores the previous tenant context
in a `finally` block. `TenantJob` re-resolves active council/module state, bounds
retries and logs payload failures to separate council files. `TenantCache` and
`TenantStorage` namespace shared resources and reject unsafe file paths.
Real database-worker tests cover deserialization, retries, terminal failure and
subsequent work for another council. Custom context fields are cleared; nested
calls restore their caller. Central retry_after defaults to 180 seconds, above
the job's 120-second timeout. Existing billing/PDF actions remain synchronous.
`TenantScheduleRunner` isolates council failures; audit verification is registered
daily at 02:00 Africa/Harare. The host must run Laravel's scheduler.

### Cross-council reporting

Not implemented. Explicit authority and auditing must be designed before any
cross-council aggregate is exposed.

## 4. Identity, roles and modules

- `users` is a central identity table; a person can hold memberships in several
  councils and can be staff in one and a citizen in another.
- `council_memberships` carries `member_type` (`staff`/`citizen`), status and a
  role. `roles.permissions` is a JSON array of permission codes; `['*']` is the
  council administrator.
- Permissions are declared by module manifests (`config/modules.php`).
  `PermissionService` grants a permission only when the membership is active,
  the role contains it, and the owning module is enabled for the council.
- `Gate::before` routes permission-named abilities through that service; policies
  still run for non-permission abilities.
- Privileged roles set `requires_mfa`. `EnsureMfaVerified` redirects to TOTP
  enrolment or challenge and requires verification within 12 hours. TOTP is a
  local RFC 6238 implementation (`TotpService`) with hashed recovery codes.
- API tokens are Sanctum tokens with abilities `council:CODE`, `portal|staff`
  and the member type. Tokens expire after 30 days and can be revoked.

### Modules

`config/modules.php` is the manifest registry: identifier, version, description,
dependencies, permissions, availability and a core flag. State is stored in
`council_modules`. `ModuleRegistry` enforces:

- core modules (`platform.core`) cannot be disabled;
- a module with active dependants cannot be disabled;
- unavailable modules cannot be enabled;
- routes declare `module:accounting` and are blocked server-side;
- tenant scheduled jobs re-resolve active council/module state before work.

## 5. Accounting engine

- **Money is never a float.** `Money` stores integer minor units and rejects
  float input; `Decimal` converts fixed decimals to scaled integers with
  half-away-from-zero rounding. Database columns are `bigint` for money and
  `numeric` for quantities and rates.
- **Chart versions** are imported through staging (`chart_import_batches` and
  `chart_import_rows`): parse, validate, approve. Codes are strings, so leading
  zeros survive. Duplicate codes, missing parents, cycles, bad classes and bad
  dates become row errors. Approval inserts `gl_accounts`, links parents,
  supersedes the previous active version and activates the new one. A demo chart
  carries `production_blocker = true`.
- **Journals** have `journal_entries` and `journal_lines`. `PostingService::post`
  requires at least two lines, exactly one non-zero side per line, non-negative
  amounts, a balanced total, an active chart, postable and active-dated accounts,
  valid dimension codes/values and an open period. It writes inside a tenant
  transaction, allocates an entry number through a locked sequence row, and is
  idempotent on `idempotency_key`, `(source_type, source_id)` and the database
  unique constraints.
- **Immutability.** A posted `JournalEntry` may only change its reversal links;
  amounts, accounts, dates and descriptions are frozen. Posted entries cannot be
  deleted. `PostingService::reverse` creates a separate balanced entry with
  debits/credits swapped, links both directions and is itself idempotent.
- **Periods** (`financial_years`, `financial_periods`) are effective-dated.
  Posting to a non-open period is rejected.
- **Reports** are queries over posted lines, never stored aggregates:
  trial balance, general ledger, financial position and financial performance.
  The position includes the current-period result and returns an equation check.
- **Posting rules** map an event code to a debit/credit account pair and required
  dimensions, with approval state. The demo chart seeds four approved rules.
- Every posting writes an audit event.

## 6. Revenue cycle

### Master data

`parties` (individual/organisation) hold multiple dated `party_roles` and
`contact_points`; a party is not an account. `properties` reference a ward and
carry decimal GPS coordinates and land use. `property_valuations` are dated and
must be approved to be used. `ownership_interests` are dated, share-limited and
approved; ownership changes never move historic debt. `customer_accounts`
reference a property and a primary liable party, and
`account_liabilities` records explicit dated liability. `service_connections`
and `meters` preserve replacement history. `meter_readings` record previous
reading, consumption, source (actual/estimated/rollover), photo document, GPS,
capture user and abnormal flag.

### Tariffs and billing

`tariff_versions` are effective-dated and approved; `tariff_bands` hold
progressive ranges. The calculator supports `metered` (progressive bands with
fixed charge and minimum), `valuation` (cents per $100 of approved valuation,
fixed charge, proration) and `fixed` (prorated). Every result carries a
breakdown used for the customer-facing explanation.

A billing run moves `previewed → approved → posted`:

- preview computes charges into `billing_run_items` with a calculation snapshot
  (engine version, tariff, reading, consumption, source, explanation, period);
  it is idempotent on a key and never creates bills;
- approval requires a different officer from the preparer (separation of duties)
  and locks control totals;
- posting processes 100 items at a time, skips items that already have a bill
  and creates bills, bill lines, snapshots and balanced journals. A partial
  unique index on `(customer_account_id, period_start, period_end,
  service_type)` prevents duplicate active bills.

Water billing uses the latest confirmed/captured reading inside the period and
falls back to the average of the last three actual consumptions, marking the
result `estimated`. Rates require an approved valuation. Refuse is a fixed
charge.

### Cash, receipts, payments

- A cashier opens a session; capture creates a verified payment, one receipt
  (`payment_id` unique), oldest-first allocations and a balanced journal
  (debit cash/bank, credit receivables, credit unapplied funds for any excess).
  Closing computes expected cash from verified cash tenders plus the opening
  float and records the variance.
- Online payments use `payment_intents → payment_attempts → payments`. The
  sandbox gateway verifies an HMAC signature over timestamp and raw body,
  enforces a 5-minute tolerance and rejects replayed nonces. Settlement is
  idempotent on the intent and the provider reference. A receipt is created
  only inside server-side settlement, never from a browser return.
- Overpayments remain as an unapplied-funds liability (account `2050`).

### Bank reconciliation

Statements are imported from CSV into `bank_statements` and
`bank_statement_lines` with a file hash and duplicate protection. Suggestions
match verified payments by amount and date (100% when the reference also
matches, 70% otherwise). Confirming a match marks the line matched and records
`bank_import` as the verification source. Reconciliation compares the GL bank
account balance with the statement closing balance.

## 7. Citizen portal

A portal user is a central identity with a citizen membership. `portal_account_links`
are pending until a six-digit code sent to a **verified** contact point is
confirmed; codes are hashed, expire after 15 minutes and are limited to five
attempts. `requireAccount` returns 404 for any account without an active link,
so account existence is not disclosed. Revocation is dated and audited. A user
may hold links in several councils (one membership and one tenant database per
council). Statements are generated as PDF with Dompdf.

## 8. AI

`laravel/ai` v1.3.0 is installed. AI is disabled by default and no key is
committed. `PolicyAssistantService`:

- enforces the `ai.assistant.use` permission;
- retrieves only approved policy documents for the current council, with keyword
  scoring and paragraph excerpts, before any provider call;
- refuses generation when disabled, with no match, or when the monthly budget is
  exhausted, while still showing source excerpts;
- calls the SDK with an anonymous agent, records provider, model, tokens, cost,
  duration and source count in `ai_usage_events`, and records failures without
  affecting core operations;
- returns a visible disclaimer that the output is assistance, not a decision.

There are no write tools, SQL, shell or generic tools. The council/role/record
boundary comes from the tenant connection and membership context. Prompt
injection is mitigated by instructions plus source-only retrieval; evaluation
fixtures beyond unit-level tests are not yet implemented.

## 9. Audit, documents and security controls

Every tenant has `audit_events` with a monotonically increasing `chain_index`, a
SHA-256 hash over canonical JSON and the previous hash. Writes are serialized by
a locked sequence row. Model updates/deletes throw. `audit:verify` and the audit
page recompute the chain. Platform actions (council provisioning) are recorded in
central `platform_audit_events`.

Documents are stored on a non-public disk (`storage/app/private/documents`) with
size, MIME and extension allow-lists, SHA-256, classification, scan status and
provenance. Downloads pass through `DocumentController` with
`platform.documents.view`; responses set `X-Content-Type-Options: nosniff` and
`Cache-Control: private, no-store`. No scanner is configured, so documents are
marked `not_scanned`.

Confidential licensing attachments are linked to the tenant's application
record. Downloads require either a verified account relationship or an active
council staff membership with a licensing review/management/approval/issuance
permission. Knowing an application ID or document ID does not grant access.

## 9a. Licensing and renewals

Licence types have tenant-scoped, numbered configuration versions. Submission
snapshots the effective configuration. Licences/instruments are separate from
application attempts and certificate versions; renewal issuance links the new
certificate to its predecessor. Shared billing, payment, allocation, refund and
journal services remain the only financial path. Deferred licence recognition
and stage-specific inspection/issuance fees are explicitly blocked until their
release and charge-stage workflows exist.

The browser and `/api/v1/licensing` expose citizen and staff workflows under
module and permission checks. Public QR verification resolves a council and
opaque verification ID, shows minimal certificate data and current validity,
and disables caching so suspension/revocation is promptly visible. Mobile
offline drafts are local unsent data and do not constitute applications or
payments. Expiry processing uses the configured council timezone and tenant-safe
job base. Notification records are deduplicated; no email/SMS/push adapter is
configured.

Other controls: CSRF on web routes, rate-limited login, session regeneration,
security headers, scoped API tokens, server-side authorization on every route,
and role/permission checks independent of navigation.

## 10. Key decisions and assumptions

| Decision | Reason | Reversible how |
| --- | --- | --- |
| Database per council, central identity | Requirement default; strong isolation and independent deployments | A shared-schema adapter would require a new connection strategy and migrations |
| Central `users` + per-council roles | One identity across councils without cross-database joins | Move identity per tenant if fully independent deployments are required |
| Database cache/queue/session | No Redis in the environment | Change `.env` drivers; no code change |
| No PostGIS | Extension not installed | Add PostGIS and migrate coordinates when available |
| Decimal latitude/longitude for GIS | Honest substitute; not a cadastre | Replace with geometry columns |
| TOTP MFA implemented locally | Avoids unverified package support; tested | Swap for a vetted library if desired |
| Sandbox payment gateway only | No verified gateway credentials | Implement a `PaymentGateway` adapter after API access is documented |
| Inertia for both web surfaces | One server, one auth/session model | Split the citizen portal into a separate SPA if needed |
| Chart codes stored as strings | Preserve leading zeros | None needed |

## 11. Known architectural gaps

- The tenant job base is tested with the real database worker; billing/PDF
  background jobs and production worker supervision remain follow-ups.
- No cross-council reporting/authority model.
- No consolidations, eliminations or disclosure-note engine.
- No licence, procurement, stores, asset, fleet, HR/payroll or land-allocation
  modules (unavailable modules are advertised as such).
- No OCR/extraction, bank matching AI, anomaly detection or draft correspondence.
- No malware scanner, no S3 driver configured, no backup automation.
- No mobile build, push notifications or deep links.
